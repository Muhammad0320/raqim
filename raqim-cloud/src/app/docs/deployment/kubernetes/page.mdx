# Altitude 3: The Deployment Plane

The execution layer for Raqim OS. This document outlines the physical deployment architecture for Sovereign Bare-Metal clusters.

<K8sTopologyDiagram />

## The Sovereign Philosophy

Raqim is not a stateless web application; it is a **Database Operating System**. 

Deploying Raqim requires abandoning traditional, ephemeral cloud paradigms. We strictly mandate bare-metal Kubernetes (K3s or RKE2) deployments. By operating at the bare-metal layer, we strip away the abstraction penalties of managed control planes, allowing the Raqim OS hypervisor to directly bind to physical hardware interrupts and memory allocations. We treat the cluster not as a server farm, but as a singular, distributed supercomputer.

## The Distroless Armor

When you execute a Swarm deployment, every node boots from the `ghcr.io/raqim-os/raqim-core` image. This is not a standard Ubuntu or Alpine container. It is a strictly deterministic, 40MB `scratch` binary.

There is no package manager. There is no `/bin/bash`. There are no coreutils.

By enforcing a pure distroless architecture, we achieve a mathematically near-zero attack surface. The resulting container physics mean that even if an adversary achieves remote code execution at the WASM layer, there is literally no shell environment to pivot into. The operating system is the binary, and the binary is immutable.

## The StatefulSet & Data Gravity

A classic Kubernetes `Deployment` is designed for stateless web servers, randomly scheduling pods and destroying them at will. Applying this to Raqim OS breaks the fundamental laws of data gravity.

Raqim demands a strict `StatefulSet` topology. The cryptographic identity and live vector memory of a node are intrinsically tied to its physical disk. If `raqim-0` experiences a hardware fault and crashes, the Kubernetes scheduler must mathematically guarantee that the resurrected pod is re-attached to the exact same NVMe block storage drive. 

This dedicated volume acts as the memory anchor, containing the node's Write-Ahead Log (WAL) and its LanceDB vector indices. We do not stream state over the network; we bind the execution engine directly to the silicon where the state resides.

## The Zenoh Headless Service

Standard Kubernetes networking routes traffic through a `ClusterIP` Service, effectively creating a load-balanced proxy that round-robins requests. This architecture is lethal to peer-to-peer topologies. 

Raqim agents communicate via the Zenoh protocol, requiring direct, un-proxied TCP connections to form the A2A (Agent-to-Agent) Mesh. To bypass the internal Kubernetes load balancer, we utilize a `ClusterIP: None` Headless Service. 

This configuration instructs the CoreDNS controller to return the actual, distinct IP addresses of every running pod rather than a single virtual IP. Each agent receives a stable, resolvable DNS record (e.g., `raqim-0.raqim-mesh.raqim-system.svc.cluster.local`), enabling pure point-to-point TCP firehose routing and a truly decentralized gossip network.
